WHAT CHANGED SINCE YOUR LAST RUN (both matter, read before running):

  1. GRADIENT FIX. The previous bundle divided the input-row gradient by the
     bag size L. fastText does NOT do that for cbow/skipgram, and it is
     load-bearing: a cbow window averages ~240 subword rows, so the 1/L
     gradient was ~240x too small to bootstrap while `wo` starts at zero.
     That is why your run collapsed (every cosine 1.00, king -> "peaking").
     Measured on a 25MB text8 slice, fixing it moved:
         loss     4.018 -> 2.562
         WS353   -0.123 -> 0.193
         mean cos 1.000 -> 0.584
     New flag `--input-grad` defaults to the correct `fasttext` behaviour.

  2. BATCH SIZE IS NOW A CORRECTNESS KNOB, NOT JUST SPEED.
     With the un-normalized (fastText) update, a huge batch accumulates
     hundreds of full-size gradients onto one row at once and DIVERGES
     (loss -> 1e14, I hit this). Your old run used --batch 262144. Do not.
     Use 4096-16384. The new default is 8192.
     If you ever see the loss explode, halve --batch.

  3. --dtype fp16 added. Storage of both tables is fp16; every logit and
     gradient is still computed in fp32 on the gathered slices, because an
     SGNS update is ~1e-5 against weights ~3e-3 and fp16's ulp there is
     ~4e-6 -- storing fp16 is fine, accumulating in fp16 would not be.
     Your own T4 numbers say the ceiling here is modest: embedding_bag
     fwd+bwd was 28.27ms fp32 vs 24.29ms fp16 (~14%), because this workload
     is gather-bound, not matmul-bound (matmul was 9x, but we barely matmul).
     Cell 7 measures it end to end so we get a real number instead of a guess.
